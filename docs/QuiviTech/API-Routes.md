# API Routes (`routes/api.php`)

Base prefix: `/api`. Mix of `Route::apiResource` (standard CRUD) and hand-rolled prefixed groups.

## Auth (`prefix: auth`)
`POST auth/login`, `signup`, `logout`, `refresh`, `me` — `AuthController` (JWT via `tymon/jwt-auth`).

## Public (no login)
`GET|POST /customer/public/{token}` — hash-link based customer self-update (`CustomersController@publicShow/publicUpdate`).

## Standard `apiResource` CRUD
`employee`, `suppliers`, `categories`, `sub-categories`, `craft`, `care`, `serves`, `product`, `expens`, `customer`, `brand` — each maps to its `*Controller` (index/store/show/update/destroy).

Extra customer routes: `generate-update-link`, `approve`, plus custom `show`/`update`.

**Shared `index()` logic, extracted 2026-07-29:** `brand`, `craft`, `categories`, `sub-categories`, `suppliers`, `care`, and `product` — the 7 pages migrated so far in the List Page Standardization initiative — now share their filter/sort/paginate boilerplate via `app/Http/Controllers/Concerns/FiltersSortsAndPaginates.php` (a trait, not a base controller, so each controller's `index()` stays an explicit, readable list of which filters it applies). `sub-categories` and `product` are the two exceptions with a fully custom sort branch (a `leftJoin`-based `category`/`sort_by=category` column in both cases), but both still use the trait's filter/pagination/response helpers. This extraction also fixed 3 bugs present identically across all 6 controllers migrated up to that point: (1) an array-shaped filter value (e.g. `?name[]=a&name[]=b`) previously crashed with `ErrorException: Array to string conversion`, now silently ignored; (2) a non-numeric/empty `per_page` previously clamped to `1` instead of the intended default of `10`; (3) `%`/`_` characters in a filter value previously acted as unintended LIKE wildcards, now escaped. **Any future batch adding a new paginated list page should use this trait from the start** rather than hand-copying the filter/sort/paginate pattern again.

**`sub_category` deviates from plain CRUD as of 2026-07-29** (Batch 5 of the List Page Standardization initiative — see [[Work-In-Progress]]), same shape as `brand`/`craft`/`category`: `GET /sub-categories` takes `page`/`per_page`/`sort_by`/`sort_dir`/`name`/`code`/`name_starts_with`/`code_starts_with`/`category_id`/`year`/`month` and returns `{success, data: [...], meta: {total, per_page, current_page, last_page}}`, with each item's `category` relation eager-loaded. `sort_by` is allow-listed to `['name', 'code', 'category', 'created_at']`; `sort_dir` to `['asc', 'desc']`; both fall back silently to `name`/`asc` on an invalid value. Filtering by category (`category_id`) is a plain `where('cat_id', ...)`, since `cat_id` is a foreign-key column on `sub_categories` itself — but **sorting** by category (`sort_by=category`) requires a `leftJoin` against `categories` (ordering by `categories.name`, not a column that exists on `sub_categories`), with `select('sub_categories.*')` to keep the join from polluting result columns, and a table-qualified `orderBy('sub_categories.id', $sortDir)` tiebreaker so the join doesn't make the tiebreaker ambiguous. `leftJoin` (not `innerJoin`) is deliberate — a `sub_category` row with a null or orphaned `cat_id` must still appear when sorting by category, just sorted as if its category name were empty. `per_page` is clamped to `[1, 100]`. A new `GET /sub-categories/filter-options` route (`SubCategoriesController@filterOptions`) is registered before the `apiResource('/sub-categories', ...)` line, same reasoning as `brand`/`craft`/`category`; it returns `{success, data: {name_starting_letters, code_starting_letters, available_years}}` (category options are NOT included here — the frontend already sources the category dropdown from the existing `GET /categories/all` endpoint). A new **`GET /sub-categories/all`** (`SubCategoriesController@all`) returns a plain, unpaginated, name-sorted JSON array with the `category` relation eager-loaded — added proactively in this same batch (unlike `categories/all`, which was a same-day reactive fix after Batch 4 shipped) for the two pre-existing bare-array consumers `pos/index.vue` and `order/edit.vue`. `create()`/`store()`/`show()`/`update()`/`destroy()` untouched (including `store()`'s pre-existing bug validating name-uniqueness against the `categories` table instead of `sub_categories` — out of scope). Rejecting or leaving an order pending no longer produces a `craft_data_id` at all. **`order.vue`'s "Today's Orders" backend (`GET /api/orders/today`) gained sort support as of 2026-08-02** (Batch 29 of the List Page Standardization initiative — see [[Work-In-Progress]]; first of two Orders-pages batches — `allorder.vue`, the larger "All Orders" page, is deliberately deferred to its own follow-up batch). `sort_by` allow-listed via `resolveSortAndApply` to `['order_id', 'total', 'order_date', 'created_at']` (the columns `order.vue`'s table actually renders). The **backend** default is `id`/`desc` — exactly the pre-change `->orderByDesc('id')` order — but note that default is never actually exercised by the only consumer: `order.vue` initialises `sortState` to `order_id`/`desc` and always sends `sort_by`, so **the page's first-load order did change** from `id desc` to `order_id desc`. `order_id` is `varchar(191)` (`QV-<prefix>-NNNNNN`), so this is a lexicographic sort, and it does **not** always agree with `id desc`: live data contains two different prefixes (`QV-BPLD-*` and the newer `QV-BLDP-*`), so across prefixes the two orders diverge. Within a single business day — which is all this endpoint ever returns — the prefix is uniform and the zero-padded counter makes `order_id desc` equivalent to `id desc` in practice, so the visible impact is nil; it is recorded here only so the difference isn't mistaken for a bug later. Only **3 of the 4** allow-listed columns have clickable headers: `order_date` and `created_at` are rendered stacked inside a single "Date" `<th>`, and `SortableTh` renders one `<th>` per sort key, so `created_at` is allow-listed but unreachable from the UI (harmless — it is still a valid `sort_by` value for direct API callers). `total` is `varchar(191)` in the live DB, so it is CAST to DECIMAL for a numeric sort. Response shape is UNCHANGED — still a bare JSON array, not the initiative's usual `{success,data,meta}` shape, and deliberately NOT paginated, since this page's stat cards are computed from the full day's order set and the natural data volume (one business day) doesn't need real pagination. This is a genuine architectural deviation from the initiative's usual template, made explicitly, not an oversight. The per-row `->map()` computing `time_remaining`/`months_remaining`/`days_remaining`/`care_price` (the QuiviCare membership countdown) is unchanged and still runs after the SQL sort. **`GET /api/orders` (`OrderController::getorders()`), the "All Orders" backend, is untouched by this batch** — it has **8** confirmed external consumers (`customer_progress`/`care_data`/`inventory_movement`/`serve_data`, each contributing both a `create.vue` and an `edit.vue` order-picker dropdown — 4 page-families × 2 = 8 files; corrects this note's earlier count of 6) treating it as a bare-array lookup; migrating `allorder.vue` needed a NEW dedicated endpoint rather than converting this one, per the project owner's decision, to avoid breaking those 8 consumers. That new endpoint, `GET /api/orders/all`, shipped in Batch 31 — see below.

**`allorder.vue`'s "All Orders" backend (`GET /api/orders/all`, `OrderController::allOrders()`) as of 2026-08-02** (Batch 31 of the List Page Standardization initiative — see [[Work-In-Progress]]; second and final of the two Orders-pages batches). Uses the shared `FiltersSortsAndPaginates` trait. Params: `page`, `per_page`, `sort_by` (allow-listed to `order_id`/`total`/`order_date`/`created_at`/`customer_name`), `sort_dir`, and filters `order_id`, `customer_name`, `customer_email`, `total`, `approve`, `date_from`, `date_to`. Response shape is the initiative's standard `{success, data, meta}`. `customer_name` is a hand-kept join-based sort special case (the trait's flat allow-list can't express joined-column sorts), matching `serve_data`'s Batch 25 precedent. `total` is `varchar(191)` in the live DB, so it is CAST to DECIMAL for a numeric sort, same as `order.vue`/Batch 29 above. The `approve` filter is tri-state: `1`/`0` filter to approved/rejected, the literal string `'null'` filters to draft (unset) orders, and omitting the param or passing an empty value applies no filter at all. `allOrders()` is a **sibling** of `getorders()` and `today()` — it does not replace either; `getorders()` remains the bare-array endpoint for the 8 external picker consumers above, and `today()` (Batch 29) remains the unpaginated single-day endpoint for `order.vue`'s stat cards.

**`employee` and `expens` migrated to standardized sorting/pagination as of 2026-08-02** (Batch 32 of the List Page Standardization initiative — see [[Work-In-Progress]]). Both `EmployeesController::index()` and `ExpensesController::index()` previously returned a bare `Model::all()` with no params at all (not the unvalidated-`orderBy()` bug class fixed elsewhere in this initiative — there was no sort param to begin with); both now use the shared `FiltersSortsAndPaginates` trait and return `{success, data, meta}`. `GET /employee` takes `page`/`per_page`/`sort_by`/`sort_dir`/`search` (matching `name`/`phone`/`email`), `sort_by` allow-listed to `['name', 'phone', 'join_date', 'created_at']`, defaulting to `created_at`/`desc`. `GET /expens` takes the same shape with `search` matching `details`, `sort_by` allow-listed to `['details', 'amount', 'expenses_date', 'created_at']`, defaulting to `created_at`/`desc`. **`expens.amount` is `varchar(191)` in the live schema** — the same numeric-stored-as-varchar trap as `order.total` (Batches 29/31) and `care_data.price` (Batch 24) — so it is CAST to DECIMAL via `castNumericColumns` for a correct numeric sort. Both tables have 0 live rows in the dev DB; verification used temporary test rows, inserted and cleaned up, per the `inv_excl_serve`/Batch 21 precedent. `store`/`show`/`update`/`destroy` untouched on both controllers. `SalariesController::index()` is deliberately NOT part of this batch — it is dead code with no route bound to it (confirmed via `grep 'SalariesController@index' routes/api.php`), and is now permanently scoped out rather than deferred, since `salary/index.vue` is actually a month-picker consuming bespoke `salary()`/`salaryview()` endpoints, not a plain record list. (Update, Batch 33: `salary/index.vue` and the `salary()`/`salaryview()` endpoints did get their own batch after all — see the Batch 33 entry below — but `SalariesController::index()` itself stayed permanently unused, not repurposed.)

**`salary` migrated to standardized sorting/pagination as of 2026-08-03** (Batch 33 of the List Page Standardization initiative — see [[Work-In-Progress]]; this is the FINAL batch of the initiative). `GET /api/salary` is unchanged: a bare array of distinct salary months, no params, no pagination — `salary/index.vue` gained client-side `SortableTh` sorting against this already-fetched-whole array (same `serves`/Batch 30 pattern), so no backend work was needed here. `GET /api/salaryview/{id}` (`SalariesController::salaryview()`) now uses the shared `FiltersSortsAndPaginates` trait and returns `{success, data, meta}`; **note `{id}` is a month-name string, not a numeric id** — a pre-existing route-naming quirk, not something this batch changed. It takes `page`/`per_page`/`sort_by`/`sort_dir`/`search`, joining `salaries` to `employees`. `sort_by` is allow-listed to `['name', 'phone', 'amount', 'created_at']` (external param names), defaulting to `salaries.id`/`desc` when no `sort_by` is sent (functionally indistinguishable from `created_at`/`desc` given the tiebreaker, since the frontend always sends explicit params); `salary_date`/`salary_month`/`salary_year`/`emp_id` are deliberately not sortable (`salary_date` is stored non-ISO d/m/y so lexicographic sort would be wrong; `salary_month`/`salary_year` are meaningless within an already-single-month-scoped result; `emp_id` has no business value to sort by). **`salaries.amount` is `varchar(191)` in the live schema** — the same numeric-stored-as-varchar trap as `expenses.amount` (Batch 32), `order.total` (Batches 29/31), and `care_data.price` (Batch 24) — so it is CAST to DECIMAL via `castNumericColumns`. **Two real bugs were found and fixed**: (1) `search` previously matched `salary_month`, a column constant across every row on this already-month-scoped page, making the search box a permanent no-op in practice; fixed to match `employees.name` instead. (2) both `salaries` and `employees` have a `created_at` column, so `sort_by=created_at` produced an ambiguous-column SQL error against the join; fixed via a request-param remap inside `salaryview()` that rewrites incoming `sort_by=created_at` to `salaries.created_at` before calling `resolveSortAndApply`, while the external param name stays the plain `created_at` (the internal allow-list literal is actually `['name', 'phone', 'amount', 'salaries.created_at']` — passing `sort_by=salaries.created_at` verbatim is also silently accepted as a side effect, harmless since it's a fixed, in-allow-list string with no injection surface). `salary/viewsalary.vue` was migrated to the shared `PaginationControl`/`SortableTh`/`sortablePaginationMixin` stack to consume this shape. `salary/allemp.vue` was NOT touched by this batch (already fixed in the Batch 32 hotfix documented above, commit `f006234`). `paid/{id}` untouched. **With Batch 33 closed, the List Page Standardization initiative is complete** — see [[Work-In-Progress]] for the full closing note.
