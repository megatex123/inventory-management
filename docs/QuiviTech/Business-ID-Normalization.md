# Business-ID Normalization

Human-readable business/display IDs (e.g. `QV-CUST-000123` — distinct from the raw auto-increment `id` primary keys) used to be generated by ~25 separate, independently-written inline blocks scattered across controllers, no two quite alike: different padding widths, different placement of date segments, and one outright copy-paste bug. `App\Support\BusinessId::next()` (added 2026-07-27) is the shared helper that replaces the ones named below.

## The helper

```php
App\Support\BusinessId::next(string $table, string $column, string $prefix, int $pad = 6): string
```

Generalizes what `ProductWarrantyController::generateSerialNo()` already did (its own in-code comment references "the Normalize ID spec" — that function was the original prior art this helper is modeled on, and now calls the helper itself instead of duplicating the logic). Looks up the highest existing value matching `{prefix}%` via `ORDER BY id DESC`, extracts the trailing number, increments, zero-pads. No locking/retry — matches this app's existing, accepted risk posture for business-code generation (a read-then-write race under concurrent creation is a known, accepted characteristic, not something this helper newly introduces).

## Entities migrated (full backfill — existing rows renumbered, not just new records going forward)

| Entity | Column | New format | Generated in |
|---|---|---|---|
| Customer | `customers.customer_id` | `QV-CUST-000001` (6-digit) | `CustomersController` |
| Meeting | `meetings.meeting_id` | `QV-MEET-000001` | `MeetingController` |
| QuiviCraft | `order.order_id` | `QV-ORDR-000001` | `PosController` |
| QuiviServe | `serve_data.serve_id` | `QV-SRV-000001` | `OrderController::updateserve()` |
| QuiviCare (new top-level) | `care_data.care_data_id` **(new column)** | `QV-CARE-000001` | `OrderController::updatecare()`, `CareDataController::store()` |
| Supplier | `suppliers.supplier_id` | `QV-SUPP-000001` | `SuppliersController` |
| QuiviCare Inventory | `inv_care.inv_care` | `IC-{category.name}-0001`, e.g. `IC-CPU-0001`, `IC-PER-MON-0001` — **4-digit, per-category** (each category's `categories.name` lookup value forms its own independent sequence, since the LIKE-prefix lookup includes the category segment) | `InvCareController` |
| Product Warranty (prior art, now deduped) | `product_warranties.serial_no` | `QV-WRTY-000001` (unchanged format — this entity already had the target scheme; only its own duplicate implementation was removed) | `ProductWarrantyController::generateSerialNo()` |

**Bundled correctness fix, not a full renumbering**: `inv_thread.inv_thread_id`'s prefix was `I-QVMR-XXXX`, identical to the unrelated InvMerch entity's own prefix (a copy-paste bug in the inline generator). Fixed to `I-QVTD-XXXX`, still 4-digit. InvMerch itself is untouched. Confirmed against live data that this was a latent bug in the code only — the actual seeded `inv_thread` rows already used `I-QVTD-` (apparently anticipated by whoever wrote the seed data), so no real collision had ever occurred and the fix produced zero disruption to existing IDs.

**QuiviCare tier sub-code** (`care_data.care_id`, the *existing* column — separate from the new `care_data_id` above): was generated two different, inconsistent ways depending on entry point — auto-create on order approval produced `{full tier code}-{seq}` (e.g. `COR3-1402-0001`), the manual `/api/care-data` form produced `{3-char truncated code}-{today's month/year}-{seq}` (e.g. `COR-2712-0001`, drifting with creation date rather than the tier's own fixed code). Both entry points — plus a third, previously-undiscovered regeneration path in `CareDataController::update()` (fires when a record's care tier is changed after creation) — now call `BusinessId::next('care_data', 'care_id', "{$tierCode}-", 4)`, unifying on the first format. **Stays 4-digit — this was a format-consistency fix, not a padding change, so it was not included in the backfill command**: verified against live data that all existing rows already happened to use the canonical format, so there was nothing to backfill in practice, but a dataset with old-format rows (if one is ever found, e.g. in a production import) would need a manual one-off fix, not this initiative's backfill command.

## Deliberately out of scope, unchanged

- `order.invoice_id` — a workflow/billing artifact set later at approval (`QVT-INV-{month/year}-{raw PK}`), not the order's own identifier.
- `serve_data.qvse_cid` — QuiviServe's own tier sub-code, same category as `care_id`'s tier segment above; not touched.
- `care_warranties.*` — including a discovered pre-existing bug where `i_qvca_id` actually stores a `product_warranties.id` raw integer rather than an InvCare business code (see [[Work-In-Progress]]).
- Every other inline generator not named in the table above: `onsite_handovers`, `onsite_handovers_studio`, `thread_orders`, `plus_orders`, `merch_orders`, `plus_services`, `merch_items`, `inv_merch`, `inv_excl_merch`, `inv_excl_serve`, `inv_move`, `serve_bek`, `serve_mps`, `serve_pce`'s own tier IDs. They keep their current inline logic — adopting `BusinessId::next()` for these is a natural follow-up, not bundled into this initiative.
- Master SKU, PC Parts codes, the new Stock subsystem, "Built Draft Proposal," QuiviCare Claim, QuiviCare Substitute/loaner tracking — all previously deferred design decisions, unaffected.

## Backfill command

```
php artisan business-id:backfill {entity?} --dry-run
```

`{entity?}` — one of `customer`, `meeting`, `order`, `serve`, `care`, `supplier`, `inv-care`; omit to run all seven. `--dry-run` prints a before/after table without writing. Renumbers in `id ASC` order (per-category `id ASC` for `inv_care`), starting each sequence at `000001`/`0001`. Re-runnable per environment — rows already matching the new format are skipped. Ran once against local dev 2026-07-27 (11-12 rows per table); output reviewed and spot-checked directly against the DB before and after.
