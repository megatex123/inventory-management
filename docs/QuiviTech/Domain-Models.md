# Domain Models

Grouped by business area. All models live in `app/Models/`. Most use `SoftDeletes`.

## Core catalog / people
- `Products` → belongsTo `Categories` (via `car_id`)
- `Categories`, `SubCategories` (belongsTo `Categories` via `cat_id`), `Brand`, `Craft`
- `Suppliers`, `Customers` → hasMany `Order`
- `Employees`, `Salaries`

## Orders / POS
- `Order` — central hub: belongsTo `Customers`, `Craft`, `Serves`, `Care`; hasMany `ServeData` (`order_id`), hasMany `CareData` (`order_id`)
- `OrderDetails` — belongsTo `Order`, belongsTo `Products` (`pro_id`); `hasOneThrough` (check for warranty linkage)
- `Cart`, `Extra`

## Repair/service domain ("Care" = repair jobs, "Serve" = service jobs)
- `Care` (lookup type) ← `CareData` (belongsTo `Customers`, `Care` as `lkp_care_id`, `Order`) — actual repair job records
  - `CareData` also has `hasManyThrough` (spare parts/details) and hasMany `OrderDetails`
  - `CareWarranty` — belongsTo `CareData`, `Products`, `Categories` (both `category_id` and `spare_category_id`); has string field `i_qvca_id` (currently just free text, not FK-enforced)
  - **Membership status (2026-07-11 change)** — the "Membership" Yes/No shown on the Care Data list is no longer the old `care_data.update_membership` manual toggle (that column and its create/edit UI + "membership notes" feature were removed). It's now a computed accessor: `CareData::getMembershipActiveAttribute()` / `getMembershipRemainingAttribute()`, auto-appended to JSON via `$appends`. Logic: coverage starts at `order.order_date` (fallback `care_data.created_at` if no linked order) and runs for `care.period_years` (new `Care::getPeriodYearsAttribute()` accessor, parses "3 years"/"5 years"/"10 years" → int). Active = now() still within that window. The `/api/care-data` `membership_status=active|expired` filter does the equivalent in raw SQL (`DATE_ADD(... care.period ...)`) since `index.vue` filters client-side over the full fetched array but still round-trips through the backend query. `CareDataController::statistics()`'s `membership_stats` is computed the same way (can't `GROUP BY` a PHP accessor, so it fetches with `order`+`care` eager-loaded and counts in PHP).
  - **Per-customer membership (2026-07-24, `Customers::careData()`)** — a customer can have multiple `CareData` records (one per approved order), each with its own tier/expiry per the logic above. The Customer List's "QuiviCare Membership" column doesn't show the latest order's tier — it shows whichever `CareData` record has the furthest-future `membership_expiry_date`, since an earlier order on a longer tier (e.g. VIS10N/10yr) commonly outlasts a more recent one on a shorter tier (e.g. COR3/3yr). Computed in `CustomersController::attachLongestCareMembership()`, eager-loading `careData.care`/`careData.order` and sorting by the accessor in PHP (same "can't `GROUP BY` an accessor" constraint as the statistics case above).
  - Note: `CareDataController::statistics()` was already broken before this change — `status_stats` queries a `status` column that doesn't exist on the live `care_data` table (see the untracked-column caveat above), so `/api/care-data/statistics` currently 500s regardless of the membership fix. Not fixed as part of the membership change (out of scope); needs its own investigation.
  - `InvCare` (new/untracked; fixed 2026-07-02 twice, `deleted_at` fix actually applied 2026-07-13 — see below) — table `inv_care` already exists in the dev DB with its own real schema, independent of the ERD's simplified `INV_QVCA`. Real columns: `inv_care` (business code, e.g. `IC-0001`), `care_id` (belongsTo `CareData`, not `Care` — despite the name it points at a specific customer's care record, not the tier lookup; the "Inv QVCA" spec CSV has no such column at all, so treat this as a loose/optional reference, not a strict business rule), `sku_code` (string, joins to `master_sku.sku_code` — not an FK id, and `InvCareController::store()` validates `exists:master_sku,sku_code` so the SKU must already exist), `item_name`, `unit_cost`, `max_stock`, `current_stock`, `category` (int, FK-ish to `categories.id`), `status`, `generate_id`, `serial_label`, `warranty_starts/duration/ends`, `manufacturer`. Model has `masterSku()` (belongsTo via `sku_code`/`sku_code`), `careData()`, `categoryLookup()`.
  - **`inv_care.deleted_at` NOT NULL bug (found 2026-07-13)** — migration `2026_07_02_150000_fix_inventory_tables_schema.php` was written to fix this (and `inv_excl_serve.deleted_at`, and `master_sku.product_raw_id`) but was **never actually applied** to the live `quivi` DB — it wasn't in the `migrations` table at all, and running it via `php artisan migrate --path=...` fails outright with "Changing columns... requires Doctrine DBAL" (the `->change()` Doctrine/DBAL gotcha — see [[Dev-Setup]]). `master_sku.product_raw_id` had separately already been made nullable by some other means, but `inv_care`/`inv_excl_serve.deleted_at` were still `NOT NULL`, which meant **every** `InvCare::create()` / `InvExclServe::create()` call would 500 (SoftDeletes never sets `deleted_at` on insert, violating the NOT NULL constraint) — this had never been hit before because both tables had 0 rows. Fixed for real this time via raw `ALTER TABLE ... MODIFY deleted_at DATETIME NULL DEFAULT NULL` against both tables (session-scoped `sql_mode=''` to tolerate the zero-date defaults mid-ALTER, same trick the migration file itself uses), then manually inserted a `migrations` row for `2026_07_02_150000_fix_inventory_tables_schema` (batch 14) so `migrate:status` stops lying about it. **Do not trust `migrate:status` alone for this repo's untracked tables — always verify the live column nullability directly if a create is failing.**
  - Seeded 6 dummy `inv_care` rows (spare/RMA replacement parts — spare CPUs, GPUs, RAM) tied via `care_id` to existing `CareData` records, plus 5 new `master_sku` rows for the spare-part SKUs (`QVSK-SPARE-*` codes) since `sku_code` must already exist in `master_sku`. 3 of the corresponding `CareWarranty` dummy records (`QV-CLA-0001`, `0003`, `0006` — the ones with `eligible_qvca=true`) had their `i_qvca_id` updated from placeholder text to the real `inv_care` business codes (`IC-0001`, `IC-0003`, `IC-0006`), completing the `CareData` → `CareWarranty` → `InvCare` chain end-to-end.
- `Serves` (lookup type) ← `ServeData` (belongsTo `Customers`, `Serves` as `lkp_serve_id`, `Order`) — actual service job records
  - Sub-types, each belongsTo `ServeData` via `serve_data_id`: `ServePce`, `ServeMps`, `ServeBek`
  - **ServeData/ServeMps/ServeBek auto-creation on order approval, and its bugs (found + fixed 2026-07-12)** — `OrderController::updateApprove()` (approve=1) calls `updateserve()`, which creates a `ServeData` row for the order (tier picked from `order.total`: <7000 BEK, <10000 MPS, else PCE — same bands as the Craft/Care tier logic) and then a matching stub `ServeBek`/`ServeMps`/`ServePce` row keyed to it. Two real bugs found while wiring the order-row quick-launch buttons below: (1) the `ServeBek`/`ServeMps` stub-creation calls never set `serve_bek_id`/`serve_mps_id`, which are `NOT NULL` columns — this crashed order approval outright for any Essential Kit/Prime Series order (never caught before because every order approved so far happened to be Collector's Edition tier); fixed by generating `{serves.code}-{sequence}` codes the same way the PCE branch already did. (2) `ServeBek::$fillable` was missing `serve_bek_id` entirely — even after fixing the create() call, Eloquent silently dropped the key on mass-assignment (no error, just a NOT-NULL constraint violation with the column absent from the generated SQL, which is what actually cost the debugging time — looked exactly like a stale-code/opcache problem until `ServeMps::$fillable` was checked for comparison and found to correctly include `serve_mps_id`). Added `serve_bek_id` to `ServeBek::$fillable`.
  - **Order-row quick-launch buttons for MPS/BEK (2026-07-12)** — mirrors the existing Craft Inspection buttons on the order list (`allorder.vue`), which link straight to `/order/:id/inspection/:phase/:round` and resolve/auto-create server-side rather than making staff search for a QVSE CID first. New: `ServeBekController::getByOrder($orderId)` / `ServeMpsController::getByOrder($orderId)` (`GET /api/serve-beks/order/{orderId}`, `GET /api/serve-mps/order/{orderId}`) — resolve `ServeData` by `order_id`, verify the tier matches (1=BEK, 2=MPS), then find-or-create the `ServeBek`/`ServeMps` row (properly setting the business id this time) and return its `id`. `allorder.vue`'s `goToServeRecord(order, tier)` calls this then `$router.push`es to the existing `servebekedit`/`servempsedit` route. Button only shows when `order.approve == 1` (since `ServeData` doesn't exist before approval) and `order.serve_id` matches the right tier. **PCE was deliberately left out of this pattern** — it already has its own richer create/edit flow (see the annual-services note below) and wasn't part of this request.
  - `ServePce` annual-services block (2026-07-11 restructure) — each of the 4 QuiviServe PCE claim perks is now its own description-field-plus-per-year-claim group, matching how the pre-existing "Free Annual Deep Cleaning" block was already shaped: `annual_dust_cleaning` (description) + `annual_dust_cleaning_year{1,2,3}` + `claim_date_year{1,2,3}` for years 1-3; `dust_cleaning_50_description` + `dust_cleaning_50_year{4,5,6,7}` + `dust_cleaning_50_claim_date_year{4,5,6,7}` for 50%-off dust cleaning (years 4-7); `upgrade_service_50_description` + `upgrade_service_50_year{1,2,3}` + `upgrade_service_50_claim_date_year{1,2,3}` for 50%-off upgrade service (years 1-3); `upgrade_service_30_description` + `upgrade_service_30_year{4,5,6,7}` + `upgrade_service_30_claim_date_year{4,5,6,7}` for 30%-off upgrade service (years 4-7). Replaces the old flat `50_dust_cleaning`/`50_upgrade_service`/`30_upgrade_service` Yes/No columns, which had no per-year claim tracking and were dropped. Migration: `2026_07_11_090000_restructure_serve_pce_annual_services.php` (plain add/dropColumn, no Doctrine/DBAL `change()` involved, ran cleanly via `--path`). See [[Frontend-Components]] for the form UI.
  - `InvExclServe` (new/untracked; fixed 2026-07-02 twice) — table `inv_excl_serve` real columns: `inv_excl_serve` (business code, e.g. `IE-0001`), `serve_data_id`, `sku_code` (string), `item_name`, `unit_cost`, `max_stock`, `current_stock`, `to_restock`, `status`, `generate_id`. Model has `masterSku()` (belongsTo via `sku_code`), `serveData()`.
- `ProductWarranty` — belongsTo `Products`

## Meetings
- `Meeting` — belongsTo `Customers`
- `MeetingDetails` — belongsTo `Meeting` — "Requirement Meeting" in the UI
- `UatMeeting` (table `uat_meeting`, added 2026-07-20) — belongsTo `Meeting`, identical schema/fillable/casts to `MeetingDetails`, just a separate list ("UAT Meeting" in the UI). No relation to `MeetingDetails` itself — two independent tables sharing the same shape by design.

## Craft inspection (build QC — single Studio Inspection step as of 2026-07-25, was 3 phases sharing one checklist)
- `CraftInspection` (table `craft_inspections`) — belongsTo `Order`; hasMany `CraftInspectionItem`. Fields: `order_id`, `phase` (column stays, `DEFAULT 2`, unused since the phase concept was dropped 2026-07-25 — see [[QuiviCraft]]), `round` (an inspection can be redone multiple rounds after a failure), `status` (default `draft`). Unique per `(order_id, round)`.
- `CraftInspectionItem` (table `craft_inspection_items`) — belongsTo `CraftInspection`, belongsTo `OrderDetails` (nullable — some component types like GPU/RAM aren't tied to a specific order line). Per-component checklist: `component_type` (cpu/mbd/gpu/ram/ssd/aio/psu/...), `fields` (JSON — free-form spec data per component type, e.g. model/serial/batch for CPU), boolean checks `model_verified`/`serial_recorded`/`factory_seal`/`qc_pass`, plus 3 stages each with a status/note/photos (JSON array of storage paths) triple: `inspection_*`, `packaging_*`, `condition_*`. Photo/note requirement by status (1-2 photos required + note optional on the good value; note required + up to 2 photos optional otherwise) is shared with `PerformanceTestChecklistItem` via `App\Http\Controllers\Concerns\ValidatesPhotoEvidence`.

## Performance testing (new QC report, Phase 1 of 4 — Assembly & Boot — added 2026-07-25)
- `PerformanceTest` (table `performance_tests`) — belongsTo `Order`; hasMany `PerformanceTestChecklistItem`. One wide table per `(order_id, round)` holding everything that occurs once per report: `cooling_solution` (`air_cooler`/`water_cooler`), 10 `overall_*` Overall-Result-summary booleans, `overall_notes`, 3 `thermal_paste_*` strings, 5 `ready_for_*` Technician-Self-QC booleans, OS Configuration (`os_installed`, `windows_activation`, `windows_update`, `os_config_note`, `os_config_photos`), Drivers Installation (6 `driver_*` booleans, `drivers_note`, `drivers_photos`), Application Installation (`applications_installed`, `applications_note`), `status` (default `draft`).
- `PerformanceTestChecklistItem` (table `performance_test_checklist_items`) — belongsTo `PerformanceTest`. Same repeated tickbox+photo+note shape as `CraftInspectionItem`'s per-stage triples, but one status per item (`pass`/`fail`) rather than 3 grouped statuses, and a `section` column (`assembly`/`boot_verification`/`bios_configuration`) instead of a component type. Unlike `CraftInspectionItem`, these 30 items (12+10+8) are a **fixed, seeded set** auto-created on first `show()` — not user-added/removable. The `assembly` section's `cooler_installation` item's `item_label` flips between "Air Cooler Installation"/"Water Cooler Installation" based on the parent's `cooling_solution`. Photo/note validation shares `ValidatesPhotoEvidence` with `CraftInspectionItem` (see above).
- **Phase 2 (Stress & Benchmark), added 2026-07-25** — `PerformanceTestCpuResult` (table `performance_test_cpu_results`), `PerformanceTestGpuResult` (table `performance_test_gpu_results`), `PerformanceTestSystemStabilityResult` (table `performance_test_system_stability_results`): each `belongsTo PerformanceTest` in a 1:1 relationship (one row per `performance_test_id`, no `round`/section column of its own — the parent's `round` already scopes it), holding that instrument's numeric readings, pass-criteria booleans, and an `overall_*_validation`/`overall_system_stability` summary boolean plus `technician_notes`. All three follow the same `SoftDeletes` + `$guarded = ['id']` convention as `CraftInspectionItem`/`PerformanceTestChecklistItem` rather than an explicit `$fillable` list. `performance_test_system_stability_results` needed an explicit short name (`pt_system_stability_results_pt_id_foreign`) on its `performance_test_id` foreign key since the auto-generated name exceeds MySQL's 64-character identifier limit.
- **Phase 3 (Memory/Storage/Cooling Validation), added 2026-07-26** — `PerformanceTestMemoryResult` (table `performance_test_memory_results`), `PerformanceTestStorageResult` (table `performance_test_storage_results`), `PerformanceTestCoolingPerformanceResult` (table `performance_test_cooling_performance_results`), `PerformanceTestCoolingSystemResult` (table `performance_test_cooling_system_results`): same 1:1-with-`PerformanceTest` shape and `SoftDeletes` + `$guarded = ['id']` convention as Phase 2's three tables. Memory and Storage each additionally carry a small flat-column "Order Specification" block directly on their own table (Expected/Detected/Status per named item — 4 items for Memory, 1 for Storage) rather than a separate child table, since both sets are small and fixed in count. No photo evidence in this phase either. `performance_test_cooling_performance_results` and `performance_test_cooling_system_results` both needed the same explicit-short-constraint-name treatment as `performance_test_system_stability_results` above (`pt_cooling_performance_results_pt_id_foreign` / `pt_cooling_system_results_pt_id_foreign`) for the same 64-character-limit reason; `performance_test_memory_results`/`performance_test_storage_results` table names are short enough that the auto-generated constraint name fits.
- **Phase 4 (Display Output/Network & Wireless/USB Port Test), added 2026-07-27 — completes Performance Testing** — `PerformanceTestDisplayResult` and `PerformanceTestNetworkResult` (1:1, same shape as every other results table — `SoftDeletes`, `$guarded = ['id']`, full `$casts`), plus a genuinely different pair for USB Port Test: `PerformanceTestUsbPort` (1:many — one row per physical port, `location` enum `front`/`rear`, seeded once with 3 fixed front ports + 4 starting rear ports; only rear ports are addable/removable) and `PerformanceTestUsbResult` (1:1, the section's own setup/pass-criteria/validation fields, separate from the port list itself). This is the first user-managed item list anywhere in Performance Testing — every other section across all 4 phases uses a fixed/seeded field or item set.

## OnSite Handover (QuiviCraft)
- **OnSite Handover (QuiviCraft), added 2026-07-27** — `OnsiteHandover` (table `onsite_handovers`): `SoftDeletes`, `$guarded = ['id']`, full `$casts`, one row per `(order_id, round)`. Unlike every Craft Inspection/Performance Testing table, this is the ONLY table for the entire feature — no child tables, since there's no repeated/swappable sub-form here (Craft Inspection has per-component items, Performance Testing has per-instrument results; OnSite Handover is a linear one-pass visit report). 6 `*_photos` JSON array columns, one per section that has a "Pictures" field in the source doc. `arrival_time` is a rare example of a field the source doc mentions in two different sections (a Report Information summary line and the fuller Arrival Verification section) that's modeled as a single column with exactly one writing endpoint (`updateArrival`) — `updateReportInfo` deliberately excludes it from its own field list.

- **OnSite Handover (Studio), added 2026-07-28** — `OnsiteHandoverStudio` (table `onsite_handovers_studio`): same shape as `OnsiteHandover` (`SoftDeletes`, `$guarded = ['id']`, full `$casts`, single table, no child tables), one row per `(order_id, round)`. 3 `*_photos` JSON array columns (arrival, post-transport, post-handover — fewer sections have Pictures than the QuiviCraft version). Reuses the exact "one column, one writer" discipline for its own `arrival_time` duplicate-field quirk.

Old routes/Vue components (`resources/js/components/document/`) removed too.

> **Important lesson (2026-07-02):** `master_sku`, `inv_care`, and `inv_excl_serve` tables already exist in the dev DB (`quivi`), created directly without migration files. My first pass at "fixing" these 3 models used the ERD PDF as the source of truth and got it wrong — the ERD is a simplified/future-state diagram, not what's actually running. The live DB schema is ground truth. Always run `DESCRIBE <table>` (or check `information_schema`) against the dev DB before trusting a model's fillable/casts, especially for untracked/WIP models with no migration file backing them.
>
> Two real schema bugs found and fixed via migration `2026_07_02_150000_fix_inventory_tables_schema`: `master_sku.product_raw_id` was `NOT NULL` (blocked all creates, since `product_raw` has 0 rows and no CRUD) → made nullable. `inv_care.deleted_at` / `inv_excl_serve.deleted_at` were `NOT NULL` (breaks Laravel's `SoftDeletes`, which sets `deleted_at = NULL` on insert and needs to `SET deleted_at = NULL`... wait, sets a timestamp on delete but needs nullable to begin with) → made nullable, zero-date rows normalized to `NULL`.
>
> `inv_care` and `inv_excl_serve` don't use an FK id to `master_sku` — they store `sku_code` (string) directly and join to `master_sku.sku_code`. Both tables also have several more `NOT NULL`-no-default columns than their conceptual ERD counterparts suggest (`category`, `status`, `generate_id`, `serial_label`, `warranty_starts/ends`, `manufacturer` for `inv_care`; `to_restock`, `generate_id` for `inv_excl_serve`) — controllers default these when the (deliberately simple) Vue forms don't collect them yet.
>
> The ERD (QuiviTech_ERD.pdf, reviewed 2026-07-02) also defines inventory/BOM entities with no model yet: `INV_QVTD`, `INV_QVPL`, `INV_QVMR`, `INV_EXCL_QVMR`, and `BOM_QVSE`/`BOM_QVPL`/`BOM_QVMR`/`BOM_DIS_QVMR`/`BOM_QVTD`. None of these have DB tables either — genuinely not built yet, out of scope until requested.
