# System-Wide Business-ID Normalization — Design

## Context

Quivitech's human-readable business/display IDs (e.g. `QVCST-0001`, `COR3-1402-0001`, `MVMT-0007` — distinct from the raw auto-increment `id` primary keys) are generated by ~25 separate, independently-written blocks of inline code scattered across controllers, no two quite alike: different padding widths, different placement of date segments, and at least one outright copy-paste bug (`inv_merch`/`inv_thread` both produce `I-QVMR-XXXX`). One entity (`ProductWarranty`) already carries a comment referencing "the Normalize ID spec" and independently implements the target scheme — this design generalizes that existing implementation into a shared helper and rolls it out to the other entities named below, including a full backfill of existing rows (not just new records going forward).

This is a scoped subset of the full renormalization idea recorded in project memory. Explicitly **deferred to future sub-projects, not touched here**: Master SKU (cross-table join key, currently free-text — highest risk), PC Parts codes, the new Stock subsystem, QuiviCraft's "Built Draft Proposal" workflow, QuiviCare Claim tracking, QuiviCare Substitute/loaner tracking.

## Audit: current state (as found, 2026-07-27)

No model uses a `boot()`/`static::creating()` hook for ID generation — every generator lives inline in a controller action. Full inventory of the ~25 call sites is preserved in the accompanying research notes; the entities relevant to this design's scope are detailed below.

**Two inconsistencies found that this design resolves as a side effect of touching this code:**
- `care_data.care_id` is generated two different ways depending on entry point: auto-create on order approval produces `COR3-1402-0001` (full tier-lookup code + sequence); the manual `/api/care-data` form produces `COR-2712-0001` (3-char truncated code + *today's* month/year, which drifts from the tier's own fixed code). These get unified.
- `inv_merch` and `inv_thread` both currently generate the identical prefix `I-QVMR-XXXX` — Thread items get Merch-branded codes. Fixed as a bundled correctness fix (not a full renumbering of either entity — just giving InvThread its own distinct prefix going forward).

**Confirmed out of scope for this design, left exactly as-is:** `order.invoice_id` (a workflow/billing artifact set at approval, not the entity's identifier — currently `QVT-INV-{month/year}-{raw PK}`), `serve_data.qvse_cid` (QuiviServe's own tier sub-code, same pattern as `care_id`'s tier segment), `care_warranties.*` (including a discovered pre-existing bug where `i_qvca_id` actually stores a `product_warranties.id` raw integer rather than an InvCare code — documented in `docs/QuiviTech/Work-In-Progress.md`, not fixed here), and every other inline generator not named in the scope table below (`meeting_details`/`uat_meeting` have no business code of their own at all — just a real FK to `meetings.id` — and stay that way).

## The shared helper

```php
namespace App\Support;

class BusinessId
{
    /**
     * Generalizes ProductWarrantyController::generateSerialNo()'s existing
     * logic (already the target scheme) into one shared helper.
     */
    public static function next(string $table, string $column, string $prefix, int $pad = 6): string
    {
        $lastValue = \DB::table($table)
            ->where($column, 'like', $prefix . '%')
            ->orderByDesc('id')
            ->value($column);

        $nextNumber = 1;
        if ($lastValue) {
            preg_match('/' . preg_quote($prefix, '/') . '(\d+)/', $lastValue, $matches);
            $nextNumber = (isset($matches[1]) ? (int) $matches[1] : 0) + 1;
        }

        return $prefix . str_pad((string) $nextNumber, $pad, '0', STR_PAD_LEFT);
    }
}
```

- `ProductWarrantyController::generateSerialNo()` itself is refactored to call `BusinessId::next('product_warranties', 'serial_no', 'QV-WRTY-')` instead of duplicating the logic inline — deduplication, not just new adopters.
- The 4-digit tier-code generators (`care_id`'s tier segment, `qvse_cid`, `inv_thread`'s new prefix) are **not** routed through this helper's default 6-digit padding — they call `BusinessId::next(..., pad: 4)`.
- **No locking/transaction wrapping is added.** This matches the existing, accepted risk posture of every other business-code generator in the app (a read-then-write race under concurrent creation is theoretically possible but has never been a reported issue at this app's traffic level) — consistent with prior precedent already accepted for ~13 other generators app-wide, not a new gap this design introduces.

## Migration: `care_data.care_data_id`

`care_data` is one of the tables created outside migration history (per `docs/QuiviTech/Domain-Models.md`) — a fresh migration adds the new column as a straightforward additive change:

```php
Schema::table('care_data', function (Blueprint $table) {
    $table->string('care_data_id')->nullable()->after('care_id');
});
```

Nullable initially so the backfill command can populate existing rows before a follow-up migration (or the backfill command itself) tightens it to `NOT NULL` + a unique index once every row has a value.

## Backfill: `php artisan business-id:backfill`

```
php artisan business-id:backfill {entity?} --dry-run
```

- `{entity?}` — optional; one of `customer`, `meeting`, `order`, `serve`, `care`, `supplier`, `inv-care`. Omit to run all seven.
- `--dry-run` — computes and prints a before/after table (old value → new value, per row) without writing anything. Run this first, always.
- Without `--dry-run`, performs the actual update, in `id ASC` order per entity (per-category-group `id ASC` for `inv_care`, since each category has its own independent sequence), starting each sequence at `000001`.
- Re-runnable per environment: the command doesn't assume it's only ever run once — if some rows already match the new format (e.g. re-run after a partial failure), it skips them and only renumbers rows still holding the old format.

## Global Constraints

- 6-digit padding applies only to the **new/top-level** IDs in the table above (`customer_id`, `meeting_id`, `order_id`, `serve_id`, the new `care_data_id`, `supplier_id`, `inv_care`). Existing 4-digit tier/sub-codes (`care_id`'s tier segment, `qvse_cid`, `inv_thread`'s corrected prefix) stay 4-digit.
- Full backfill, not just new-records-going-forward: existing rows get renumbered too, in `id ASC` creation order.
- No entity outside the scope table gets touched, including the ~18 other existing inline generators not named above — they keep their current inline logic unchanged. Adopting `BusinessId::next()` for those is explicitly out of scope for this design (a natural follow-up, not bundled in here).
- `order.invoice_id`, `serve_data.qvse_cid`, and `care_warranties.*` are explicitly out of scope, confirmed with the user — do not touch them even though they're adjacent to in-scope entities.

## Testing

No automated test suite exists for this app (established throughout this codebase). Verification is manual:
1. `--dry-run` output reviewed for correctness before any real write, for every entity.
2. After a real backfill run in the local dev environment, spot-check a handful of renumbered rows via `DESCRIBE`/`SELECT` against the live DB, confirming sequence continuity and no gaps/duplicates within a prefix group.
3. Confirm every place a business code is *displayed* (Vue list/detail pages, exports) still renders correctly post-backfill — these read the column value directly, so no frontend changes are expected, but worth a visual check per entity.
4. Confirm new-record creation (not just backfill) produces the new format going forward, for all seven in-scope entities.

## Out of Scope

- Master SKU, PC Parts codes, the new Stock subsystem, "Built Draft Proposal," QuiviCare Claim, QuiviCare Substitute/loaner tracking — all previously deferred, unaffected by this design.
- `order.invoice_id`, `serve_data.qvse_cid`, `care_warranties.care_warranty_id`/`i_qvca_id`/`care_invoice_id`.
- Adopting `BusinessId::next()` for the ~18 other existing generators not named in the scope table (`onsite_handovers`, `thread_orders`, `plus_orders`, `merch_orders`, `plus_services`, `merch_items`, `inv_merch`, `inv_excl_merch`, `inv_excl_serve`, `inv_move`, etc.) — they keep their current inline logic.
- Fixing the pre-existing `care_warranties.i_qvca_id` bug (stores a `product_warranties.id` raw integer instead of an InvCare code) — documented in `docs/QuiviTech/Work-In-Progress.md`, left for a separate follow-up.
